# CrawlerHub V1.2 需求分析：自动采集与任务运营

| 项目 | 内容 |
| --- | --- |
| 文档版本 | v0.1（评审稿） |
| 产品版本 | V1.2 |
| 编写日期 | 2026-10-25 |
| 文档类型 | 版本需求分析，非开发排期承诺 |
| 需求来源 | 现有 PRD 的 P2-02/P2-07、架构约束及 2026-10-25 产品迭代分析 |
| 核心主题 | 跑得久：从手动执行升级为可持续、可恢复、可诊断的自动增量采集 |

## 1. 背景与问题定义

V1.0 已支持手动批次、增量游标、暂停恢复、失败重试与进程重启恢复，但周期性采集仍要求用户主动进入工作页。对于追更、素材归档和定期备份场景，产品价值取决于能否长期稳定运行，而不只是单次任务成功。

V1.2 需要在不改变“本地单机单用户”边界的前提下，补齐定时调度、策略复用、事件通知和全局任务运营能力。

### 1.1 现状证据

- 当前批次由用户在工作页手动创建，未实现调度计划与通知。
- 工作页聚焦单个数据源，首页侧重运行中批次与健康度，缺少统一历史任务运营入口。
- `crawl_batch` 已具备策略参数、游标快照与状态记录，可复用现有执行引擎。
- 同源单飞由数据库约束保证，但定时触发与手动触发之间的冲突策略尚未产品化。
- V1.1 规划 `trigger_type=manual / preview`，本版本扩展 `schedule`，并补充调度幂等语义。

### 1.2 关键假设

- 调度只在应用运行时执行；应用退出期间不承诺后台系统级常驻。
- 默认不为停机期间的每次计划补跑，避免恢复后任务风暴。
- 定时采集仅用于公开或已授权内容，并遵循目标站点条款与合理访问频率。

## 2. 版本目标与成功指标

### 2.1 产品目标

1. 用户可将已验证的数据源与策略保存为可复用配置，并按周期自动执行。
2. 自动任务不会因应用重启、同源单飞或重复触发而产生重复批次和游标污染。
3. 用户无需停留在工作页，也能获知完成、失败和需要人工介入的事件。
4. 用户可以在统一任务中心查看、筛选、诊断和干预全部批次。

### 2.2 核心指标

| 指标 | 定义与口径 | 建议目标 | 排除项与说明 |
| --- | --- | --- | --- |
| 调度触发成功率 | 成功创建唯一批次的计划触发次数 ÷ 应触发计划次数 | 建议 ≥99% | 应用未运行产生的 missed 单列，不伪装为成功 |
| 自动批次有效完成率 | `success + success_with_warning` 的自动批次数 ÷ 自动批次终态数 | 先建立基线 | 用户主动取消单列；0 新内容的空成功仍计完成 |
| 重复调度批次率 | 同一 `schedule_id + planned_at` 产生多批次的计划数 ÷ 计划触发数 | 0 | 资金级语义不适用，但幂等为调度底线 |
| 持续自动采集数据源数 | 自然周内至少有 2 个不同日期成功完成自动批次的数据源数 | 建立基线后逐版提升 | 手动与试采批次不计入 |
| 失败恢复率 | 失败批次在 24 小时内经重试或配置修改后成功的比例 | 先建立基线 | 无权限、404 等明确不可恢复失败单列 |
| 通知触达成功率 | Webhook 接收端 2xx 的通知数 ÷ 实际发送通知数 | 建议 ≥95%，按用户自建渠道观察 | 用户关闭通知不计入分母 |

> 最小数据能力：提供本地“自动采集概览”，至少展示计划数、实际触发、跳过、错过、成功、失败和通知触达情况。

## 3. 目标用户与核心场景

| 用户 | 核心诉求 | 典型场景 |
| --- | --- | --- |
| 内容运营 | 定期自动追更，并在失败时及时处理 | 每 6 小时按增量策略采集，失败率达到阈值时收到通知 |
| 个人采集者 | 一次配置长期复用，避免重复操作 | 保存常用策略，查看下次运行时间与最近结果 |
| 技术维护者 | 统一排查手动和自动任务 | 在任务中心按来源、状态、错误码筛选并处理异常 |

### 用户故事

- 作为内容运营，我希望为数据源设置定时增量计划，以便无需每天手动发起采集。
- 作为个人采集者，我希望查看下次运行时间与跳过原因，以便理解系统为什么没有执行。
- 作为技术维护者，我希望集中查看历史批次和错误分类，以便快速恢复失败任务。

## 4. 需求范围

### 4.1 本版本包含

- 策略预设的保存、编辑、复制、删除与默认选择。
- 每 N 小时和 cron 两类调度计划，支持启停与立即执行。
- 调度幂等、同源单飞冲突、停机错过和应用重启恢复规则。
- 批次完成、连续失败和高失败率通知。
- 全局任务中心、历史批次、取消、暂停、恢复和失败重试。
- 数据源级请求间隔与并发限制。
- 自动采集与任务运营本地指标看板。

### 4.2 本版本不包含

- 多节点调度、分布式队列、云任务和多租户。
- 应用退出后的系统级常驻服务安装；可作为后续独立部署需求。
- 登录态、验证码、动态签名或 DRM 处理。
- 复杂工作流编排、跨数据源依赖和条件触发。
- 产物预览、批量删除与存储治理，归入 V1.3。

## 5. 方案对比与选型

| 方案 | 成本 | 复杂度 | 用户体验 | 风险 | 综合评价 |
| --- | --- | --- | --- | --- | --- |
| A：仅提供命令行 cron 脚本 | 低 | 低 | 与零命令行目标不符 | 配置分散、状态不可见 | 不推荐 |
| B：应用内调度 + 全局任务中心 | 中 | 中 | 配置、执行和恢复闭环统一 | 需处理停机与幂等边界 | 推荐 |
| C：直接引入分布式调度平台 | 高 | 高 | 对单机用户过重 | 运维复杂、依赖增加 | 本期不做 |

推荐 B，继续复用现有单例引擎和 SQLite，不引入与当前部署形态不匹配的分布式基础设施。

### 方向级 RICE（估算）

Reach=4、Impact=3、Confidence=80%、Effort=1.5 人月（估算），RICE=`4×3×0.8÷1.5=6.4`。该分值用于版本间排序，不代表真实用户规模或排期。

## 6. 功能需求与验收标准

### V1.2-FR-01 策略预设（Must）

用户可将策略类型、参数和文字导出格式保存为数据源级预设；预设不包含输出根目录、凭据或脚本内容。

- Given 用户已在工作页验证一组策略，When 保存为预设，Then 后续可一键选择并预填所有适用字段。
- Given 预设被修改，When 已有关联调度计划，Then 页面明确受影响计划；默认调度引用预设当前版本并记录每次执行快照。
- Given 预设被删除，When 仍被启用计划引用，Then 系统阻止删除并列出关联计划，或要求先停用计划。

### V1.2-FR-02 调度计划管理（Must）

每个计划包含名称、数据源、策略预设、调度规则、启停状态、错过策略、下次运行时间和最近执行结果。

- Given 用户选择“每 N 小时”，When 输入合法间隔并保存，Then 系统计算并展示带时区的下次运行时间。
- Given 用户选择 cron，When 表达式无效或时区缺失，Then 字段级提示并阻止保存。
- Given 数据源被停用或删除，When 计划到点，Then 不创建批次，记录 skipped 及原因，并在计划列表显示需要处理。

### V1.2-FR-03 调度触发幂等（Must）

每次计划触发以 `schedule_id + planned_at` 作为唯一业务键；手动、自动与重启恢复不得重复创建同一计划批次。

- Given 同一计划同一计划时间被并发触发两次，When 创建批次，Then 数据库仅允许一条调度执行记录，最多创建一个批次。
- Given 调度执行记录已存在但批次创建失败，When 用户查看计划，Then 状态明确为 failed 并支持按同一业务键安全重试，不产生重复执行记录。
- Given 应用重启，When 调度器恢复，Then 已完成的计划时间不得再次触发。

### V1.2-FR-04 单飞冲突与立即执行（Must）

自动与手动批次共用同源单飞约束；计划到点时若同源已有活跃批次，本次默认记为 skipped，不排队堆积。

- Given 同数据源存在 pending/running/paused 批次，When 自动计划到点，Then 本次记录 skipped、占用批次 ID 和原因，并计算下一次计划时间。
- Given 用户在计划页点击“立即执行”，When 同源无活跃批次，Then 以 `trigger_type=schedule` 创建一次手动触发的计划批次，并关联计划但不改变原下次计划时间。
- Given 用户需要等待执行，When 查看冲突提示，Then 可前往占用批次；本版本不自动串联多个等待批次。

### V1.2-FR-05 停机错过与重启恢复（Must）

默认仅调度应用运行期间的未来计划；停机期间的计划记为 missed，不逐次补跑。

- Given 应用在计划时间未运行，When 应用重新启动，Then 计划展示错过的次数与最近错过时间，并恢复未来调度。
- Given 用户启用“启动后补采一次”（可选开关，默认关闭），When 检测到至少一次 missed，Then 仅创建一次补采批次，使用最新策略与增量游标，不按 missed 次数重复补跑。
- Given 进程退出时存在运行中批次，When 重启后，Then 沿用现有孤儿恢复机制，并将调度执行记录与批次结果正确关联。

### V1.2-FR-06 增量采集与频率保护（Must）

调度复用现有游标、去重、重试和全局并发语义；支持数据源级最小请求间隔与并发上限。

- Given 两次自动计划解析到同一批已成功内容，When 执行去重，Then 不重复生成正式任务，并展示“无新增内容”。
- Given 数据源配置最小请求间隔，When 解析或下载发出请求，Then 同源请求频率不超过配置值，且不使用全局并发绕过限制。
- Given 数据源级并发高于全局上限，When 执行，Then 实际并发取两者较小值，并向用户展示生效值。

### V1.2-FR-07 事件通知（Must）

提供应用内通知记录与 Webhook；事件至少包括批次完成、批次失败、连续失败达到阈值和失败率达到阈值。

- Given 用户配置合法 Webhook 并启用事件，When 批次达到触发条件，Then 发送包含事件 ID、计划、批次、状态、统计和时间的 JSON。
- Given 同一事件重复投递，When 接收端检查事件 ID，Then 可据其幂等处理；系统对超时和 5xx 采用有限退避重试，4xx 不自动重试。
- Given Webhook URL 含敏感参数，When 在界面、日志或导出中展示，Then 默认脱敏；通知正文不得包含正文、脚本或完整敏感 URL。

### V1.2-FR-08 全局任务中心（Must）

提供全部批次列表与详情，支持按数据源、内容类型、触发来源、状态、时间和错误码组合筛选。

- Given 用户打开任务中心，When 选择筛选条件，Then 手动、试采和自动批次均按统一口径展示，默认按创建时间倒序。
- Given 用户打开批次详情，When 查看执行信息，Then 可看到策略快照、游标变化、任务统计、日志、关联计划和产物入口。
- Given 列表自动刷新，When 用户正在翻页或选择批次，Then 不得无故清空筛选、选中项或跳回第一页。

### V1.2-FR-09 批次取消与恢复操作（Must）

在现有暂停、恢复和重试之外增加取消；取消不是强杀线程。

- Given 批次运行中，When 用户确认取消，Then 不再领取新任务，运行中任务在当前原子步骤后结束，pending 任务标记 cancelled，批次最终为 cancelled。
- Given 批次部分成功后取消，When 计算游标，Then 仅按已成功项推进，取消项不得在后续增量中被永久跳过。
- Given 批次已取消，When 用户查看操作，Then 不允许恢复；可基于原策略快照新建批次，并明确这是新批次。

### V1.2-FR-10 失败诊断与恢复入口（Should）

按网络、站点拒绝、解析、字段、下载、转码、磁盘和脚本聚合失败，提供对应修复入口。

- Given 多个任务因同一错误码失败，When 打开批次诊断，Then 展示主要错误、影响任务数、首次发生时间和建议动作。
- Given 错误可通过重试恢复，When 用户点击重试，Then 仅提交符合条件的 failed 任务，不重复成功任务。
- Given 错误需要修改数据源，When 用户点击修复配置，Then 跳转对应数据源并保留返回批次的路径。

## 7. 核心流程与状态规则

### 7.1 自动采集主流程

创建策略预设 → 创建并启用计划 → 到点生成唯一执行记录 → 检查数据源与单飞 → 创建自动批次 → 增量执行 → 记录结果 → 发送通知 → 计算下次运行时间。

### 7.2 调度执行状态

`scheduled → triggered → skipped / failed / batch_created`；错过为 `missed`，执行记录与批次状态分离，避免把“无新增内容”误报为调度失败。

### 7.3 关键异常

- 同一计划重复触发：唯一约束拦截，保留一次执行记录。
- 同源被占用：本次 skipped，不创建等待队列。
- 通知失败：不回滚已成功的采集批次，通知状态单独记录。
- 应用重启：恢复未来计划，历史 missed 与批次恢复分开处理。
- 修改时区或系统时间：重新计算下次运行时间并记录变更，不回放已过去计划。

## 8. 数据与本地埋点需求

### 8.1 数据实体建议

- `strategy_preset`：数据源、名称、策略快照、导出格式、时间戳。
- `crawl_schedule`：数据源、预设、规则类型、规则表达式、时区、启停、补采开关、下次运行时间。
- `schedule_run`：计划、计划时间、唯一业务键、执行状态、关联批次、跳过/失败原因。
- `crawl_batch.trigger_type` 扩展 `schedule`，并可选关联 `schedule_run_id`。
- `notification_event`：事件 ID、类型、批次、渠道、投递状态、尝试次数和最近错误。
- 批次与任务状态枚举增加 `cancelled` 时，前后端映射与数据库约束同步更新。

### 8.2 事件口径

| 事件 | 触发时机 | 关键属性 |
| --- | --- | --- |
| `schedule_created` | 计划创建成功 | 规则类型、内容类型、是否补采 |
| `schedule_triggered` | 到点生成执行记录 | 计划 ID、计划时间、触发来源 |
| `schedule_skipped` | 到点但未创建批次 | 原因、占用批次、数据源状态 |
| `schedule_missed` | 启动后发现错过计划 | 错过次数、最近计划时间 |
| `batch_cancelled` | 用户确认取消 | 触发来源、成功/待执行/运行中数量 |
| `notification_delivered` | 通知进入终态 | 渠道、事件类型、成功/失败、尝试次数 |

埋点与通知默认不记录完整敏感 URL、脚本、正文、Webhook 密钥或文件内容。

## 9. 非功能、安全与合规要求

- 单进程调度扫描在正常本地负载下不得阻塞 API；建议调度扫描间隔 30 秒，允许计划时间存在不超过一个扫描周期的延迟。
- 调度创建批次必须通过数据库唯一约束保证幂等，不能只依赖“先查再插”。
- 所有调度与通知写操作使用短事务，不跨网络请求持有数据库会话。
- Webhook 请求必须有连接与读取超时、有限重试和响应大小限制；不得因接收端故障阻塞引擎。
- 默认仅监听本机；开放局域网访问前必须另行评估认证与授权，本版本不支持无认证团队共享。
- 频率保护面向公开或已授权采集，用户需自行确认站点条款和内容使用权限。

## 10. 依赖与就绪度

| 依赖项 | 分级 | 最晚就绪时点 | 影响与替代方案 |
| --- | --- | --- | --- |
| 调度执行唯一键与幂等迁移 | 阻塞 | 调度器开发前 | 未就绪不得上线自动触发，避免重复批次 |
| 批次 `trigger_type` 与试采/正式统计口径 | 阻塞 | 数据模型评审前 | V1.1 未落地时需在本版本补齐 |
| 全局任务中心 API 与取消状态机 | 并行 | 任务中心联调前 | 调度可先上线，但不得宣称完整任务运营闭环 |
| Webhook 渠道 | 可绕过 | 通知功能联调前 | 可先提供应用内通知，Webhook 后续开启 |
| 真实长时间运行环境 | 并行 | 发布验收前 | 缺少 soak test 时不得承诺长期稳定运行 |

| V1.2-RK-05 | 取消语义破坏游标或遗留运行线程 | 2 | 5 | 10 中 | 原子步骤后退出、仅成功项推进、状态机与重启测试 |

## 12. 上线验证与需求追踪

- 同一计划并发触发、调度器重复扫描和应用重启均只能产生一个批次。
- 覆盖同源手动/自动冲突、停用源、0 新内容、部分失败、取消、暂停恢复和进程重启。
- 覆盖停机多次 missed、默认不补跑与可选仅补一次。
- 验证通知失败不影响批次，重复事件 ID 可识别，敏感字段不进入日志。
- 进行不少于 24 小时的本地连续运行验证，观察计划漂移、线程残留、数据库锁与通知积压；该时长为建议验收条件。

## 13. 待确认问题

1. 应用未运行时的 missed 是否仅展示，还是提供可选系统级常驻部署；本版本默认仅展示。
2. cron 是否需要秒级字段；本版本建议采用分钟级五段表达式。
3. 连续失败通知阈值建议默认 3 次，高失败率阈值建议 50%，是否允许按计划覆盖全局设置。
4. 计划修改策略预设后，历史批次保留执行快照，是否还需保留完整预设版本历史。
